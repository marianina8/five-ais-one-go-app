### Error handling
- **medium** — store.go:157-163, http.go:145-149 — When the rename succeeds but `dir.Sync()` fails, `commit` keeps the new state and returns the error. `Create` then answers 500 even though the link exists. A client that retries with the same alias gets 409, and a random-code create leaves an orphan link. `Delete` and `Follow` have the same problem: the change is applied but the caller sees a failure. Return a distinct "committed but not synced" result, log it, and treat the operation as successful, or document this behaviour and test it.
- **medium** — store.go:223-239 — A public redirect depends on the visit counter being saved. If the disk is full or read-only, every `GET /{code}` returns 500 even though the target URL is known. A bookkeeping failure takes down the main function of the service. Log the save error and still redirect, or at least decide this on purpose and note it in the README.
- **low** — store.go:230-232, http.go:51-61 — The "visit counter exhausted" error is a plain error, so it comes out as a generic 500. A `uint64` can't realistically reach that value, so this branch is dead code. Remove it.
- **low** — store.go:190-201, http.go:51-61 — `Create` returns plain `errors.New("invalid URL")` and `errors.New("invalid alias")`. `storeError` would turn them into 500 if they were ever reached. The handler validates first, so this is unreachable today. Export a sentinel such as `ErrInvalid` and map it to 400, or drop the duplicate checks.

### Secrets and sensitive data
- **low** — store.go:42-48 — `validURL` accepts URLs that carry credentials, for example `https://user:pass@example.com/`. I created one through `Store.Create` [verified]. The credentials are then stored in `data.json` in plain text. Anyone with the admin token gets them back from `GET /api/links`, and every visitor gets them in the `Location` header. Reject URLs where `u.User != nil`.
- **low** — main.go:16-20 — `ADMIN_TOKEN` can be any non-empty string, such as `a`, and nothing slows down guessing. Enforce a minimum length, and consider rate-limiting 401 responses.

### Input validation
- **medium** — http.go:66-70, store.go:187-221 — The unauthenticated `POST /api/links` has no cap on the number of links, no per-client limit, and no limit on total storage. Each link adds to a file that is fully rewritten on every operation. A single client can grow the file until the disk fills or requests become very slow, which also stalls every redirect. Add a maximum link count or file size, and rate limiting, or put the endpoint behind a proxy that does this. Say in the README that it is intentionally public.
- **low** — http.go:36-38 — The code accepts only the exact string `Bearer <token>`. RFC 7235 says the scheme name is case-insensitive, and the test suite pins `bearer secret` as a 401. Compliant clients are rare, so I am not asking for a change. If you leave it as is, document it.
- **low** — http.go:118-127 — The POST body is not checked for `Content-Type`. This is harmless today, but a cross-site HTML form could still create links, because the endpoint is public. Require `application/json` if you ever add authentication to this route.

### External services
- **medium** — store.go:187-257, http.go:63-105 — Every mutation, including every public redirect, takes the single global mutex and then does a full JSON marshal, a temp-file write, two fsyncs and a rename of the whole data set. I measured 5000 creates taking about 29 s in total, and 50 redirects with 5000 links taking about 5.9 ms each [verified]. That means roughly 170 redirects per second at best, getting worse as the file grows, and every request queues behind the lock. With the 30 s `WriteTimeout`, slow disks will produce timeouts. Keep visit counts in memory and flush them periodically or at shutdown, or use an append-only log or a real database. Only fsync on create and delete.
- **low** — main.go:25-36 — The server never shuts down gracefully. On SIGTERM, in-flight requests are cut off. The data stays consistent thanks to the atomic rename, but `.shortener-*.tmp` files accumulate and nothing cleans them up. Use `signal.NotifyContext` with `server.Shutdown`, and remove stale temp files at startup.

### Resources and concurrency
- **low** — store.go:149-155, 233-236 — `Follow` and `Delete` copy the whole map (`snapshot`) on every call, in addition to the full marshal. That is O(n) allocation under the lock for a one-record change. If you keep this design, mutate in place and roll back on a failed save, or accept the cost explicitly.
- **low** — store.go:123-146 — `dir` is opened before the temp file is created and is held only to be synced after the rename. This is correct, but `defer f.Close()` runs a second time after the explicit `f.Close()`, and `defer os.Remove(f.Name())` also runs after a successful rename and just returns an error that is ignored. This is harmless. A short comment would stop a future reader from wondering whether the remove can delete the live file.

### Tests
- **medium** — store_test.go, http_test.go — There is no test for the "rename succeeded, `dir.Sync` failed" path in `commit`. That is the one branch with deliberately unusual behaviour and the most surprising HTTP result. Make the sync step injectable and test that the state and the response stay consistent.
- **low** — store_test.go:94-144 — `TestSnapshotsAreAlwaysComplete` can only fail if a reader catches a partial write. It would not notice if `atomicSave` were replaced with a truncating `os.WriteFile`, because that race is rarely hit in 100 iterations. The test is weak evidence for the atomicity claim. Check instead that the temp file is written and renamed (for example by injecting a failing write and checking that the old file is intact, which `TestFailedSaveDoesNotCommit` partly does).
- **low** — store.go:167-185 — There are no tests for `randomCode` collision handling (the retry loop at store.go:203-212), for userinfo URLs, or for the `Follow` and `Delete` code paths when the file system fails mid-way.
- **low** — main_test.go:16-51 — The only `main` test covers startup failures. Nothing tests a successful start, the timeouts, or shutdown behaviour.

### Clarity
- **low** — http.go:77 — This `case` condition calls `strings.TrimPrefix(path, "/api/links/")` three times and is hard to read. In plain terms it says: the path starts with `/api/links/` and what follows is non-empty and has no slash. Compute `code, ok := strings.CutPrefix(path, "/api/links/")` once and test `ok && code != "" && !strings.Contains(code, "/")`.
- **low** — http.go:90 — `strings.HasPrefix(path, "/")` is always true for a request path, and the `path[1:]` handling is repeated at line 95. Write `code := strings.TrimPrefix(path, "/")` once and test `code != "" && !strings.Contains(code, "/")`.
- **low** — store.go:176 — The magic number 248 is `62*4`, the largest multiple of 62 that fits in a byte. The comment mentions bias but not this number. Write `const maxUnbiased = 256 - 256%len(alphabet)` and use it.
- **low** — store.go:88-97 — `requireEOF` returns the error from the second `Decode` when it is not `io.EOF`, and its own "multiple JSON values" error when that decode succeeds. The `err != io.EOF` test with a nested `err == nil` is awkward. Write it as `err == io.EOF → nil`, `err == nil → "multiple JSON values"`, otherwise `err`.
